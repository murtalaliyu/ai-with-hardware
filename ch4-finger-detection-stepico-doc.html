Technical Documentation

Line-by-line reference for ch4-finger-detection-stepico.py: MicroPython firmware that runs on a STEPico (Raspberry Pi Pico–compatible) board, reads a compact ASCII serial protocol from USB stdin, and drives two banks of five LEDs to mirror finger counts detected by the PC vision script.

MicroPython STEPico / RP2040 GPIO LEDs USB Serial stdin uselect polling

1. Overview

This script is the microcontroller half of the Chapter 4 finger-detection demo. It does no computer vision itself. Instead it waits for single-byte commands arriving over the USB serial link (exposed in MicroPython as sys.stdin), interprets them with a tiny two-step state machine, and sets GPIO pins high or low so physical LEDs light in proportion to the number of extended fingers reported by the PC.

Companion PC script

The vision / transmitter side is ch4-finger-detection-pc.py. It uses MediaPipe Hands to count fingers and writes characters such as 1+digit, 2+digit, L, R, and V to the same COM port this firmware is listening on.

Poll USB stdin (non-blocking)
Read one character when data is ready
State machine: hand select vs finger count vs test keys
Drive left or right LED bank via GPIO
Loop forever

3. Dependencies & Imports (lines 1–4)

Line 1 
from machine import Pin

Imports the MicroPython Pin class from the machine module. Pin is the hardware abstraction for a single GPIO line. Later calls like Pin(20, Pin.OUT) configure that pad as a digital output and return an object whose .value(0|1) method drives the pin low or high.

Line 2 
import time

Imports the MicroPython time module (provides time.sleep, time.ticks_ms, etc.). In this file it is never called — there is no delay or timestamp. It is likely leftover from an earlier revision that blinked LEDs or paced the loop. Harmless to leave; safe to remove for a cleaner script.

Line 3 
from sys import stdin

Imports the standard-input stream object. On a Pico / STEPico connected over USB, MicroPython maps the USB CDC serial port to sys.stdin / sys.stdout. Characters the PC writes with PySerial appear here as readable bytes. The firmware therefore does not open a UART device explicitly — USB serial is stdin.

Line 4 
import uselect

Imports MicroPython’s uselect module (a lightweight cousin of CPython’s select). Used to poll whether stdin has data ready without blocking the infinite loop. Without this, a bare stdin.read(1) would hang until a character arrived, which is fine for a simple REPL demo but less flexible if you later want to multiplex other work in the same loop.

6. LED Banks & State (lines 20–23)

Lines 20–21 
left_LEDs = [red1, orange1, white1, green1, blue1]
right_LEDs = [red2, orange2, white2, green2, blue2]

Packs each bank into an ordered Python list of Pin objects. Index 0 is the first LED lit for a count of 1; index 4 is the fifth. turn_on_LEDs iterates these lists by index, so order is part of the protocol semantics: finger count N lights LEDs [0 .. N-1].

Line 23 
hand = '0'

Initializes the protocol state machine’s “pending hand” variable to the string '0', meaning no hand selected yet. Valid transient values after a select byte are '1' (next digit applies to left bank) and '2' (next digit applies to right bank). After applying a finger count, the code resets hand back to '0'.

Using a string ('0', '1', '2') rather than an integer keeps comparisons identical to the character values read from stdin (stdin.read(1) returns a 1-character string in MicroPython).

7. turn_on_LEDs (lines 25–38)

Core actuator helper. Given a list of five LED pins and a count, turns on the first N LEDs and turns the remainder off. Also handles the special case N = 0 (all off).

Line 25 
def turn_on_LEDs(LEDs, num_LEDs):

Function signature:

  • LEDs — a list of Pin objects (either left_LEDs or right_LEDs)
  • num_LEDs — how many LEDs to light; may arrive as a string digit (e.g. '3') from serial, or as an int (e.g. 5) from the L/R test branches
Line 26 
num_LEDs = int(num_LEDs)

Coerces the count to an integer. Essential because the serial path passes a raw character such as '3'; without int(...), comparisons like num_LEDs == 0 and range(num_LEDs) would fail or behave incorrectly on a string.

Lines 28–31 
if num_LEDs == 0:
    # if no finger shows up
    for leds in LEDs:
        leds.value(0)

Zero-finger case: iterate every pin in the bank and drive it 0 (logic low → LED off for active-high wiring). The loop variable is named leds (plural) but each iteration is a single Pin.

Lines 32–35 
else:
    for i in range(num_LEDs):
        # turn on the corresponding number of LEDs
        LEDs[i].value(1)

For any positive count, light indices 0 through num_LEDs - 1 by writing logic high (1). Example: num_LEDs == 3 turns on red, orange, and white in that bank.

There is no bounds check. If num_LEDs were greater than 5 (e.g. a corrupted character that still parses as an int larger than 5, or a bug on the PC side), LEDs[i] would raise IndexError. In normal use the PC only sends digits 0–5, and the test keys hard-code 5.
Lines 36–38 
# turn off the rest of the LEDs
for i in range(num_LEDs, 5, 1):
    LEDs[i].value(0)

Clears the unused LEDs in the same bank so a previous higher count does not leave stale lights on. range(num_LEDs, 5, 1) yields num_LEDs, num_LEDs+1, …, 4. The step argument 1 is the default and could be omitted; it is written explicitly for clarity.

Example: if the bank previously showed 5 LEDs and a new count of 2 arrives, indices 0–1 go high in the first loop, and indices 2–4 go low here.

8. Main Loop & Polling (lines 40–46, 65–66)

An infinite loop continuously checks whether serial data is available and drains every pending character through the protocol parser.

Line 40 
while True:

Starts the forever loop that constitutes the firmware’s main program. There is no exit condition, sleep, or watchdog kick — the board runs this until power loss, soft reset, or the MicroPython soft-reboot (e.g. Stop in Thonny).

Lines 41–42 
# to receive input via serial communication
select_result = uselect.select([stdin], [], [], 0)

Non-blocking poll of the readable set. Arguments:

  • [stdin] — watch this stream for readability
  • [] — empty writable set
  • [] — empty “exceptional” set
  • 0 — timeout of 0 seconds → return immediately

Return value is a 3-tuple (readable, writable, exceptional). select_result[0] is a list of streams that have data; it is non-empty when at least one byte is waiting on stdin.

Lines 44–46 
while select_result[0]:
    # assign the first character to input_character
    input_character = stdin.read(1)

Inner drain loop: as long as the readable list is truthy (data pending), read exactly one character into input_character. stdin.read(1) returns a length-1 string such as '1', '3', or 'L'.

Processing one byte at a time is required by the two-byte protocol (hand select, then count): each iteration of this inner loop advances the state machine by one character.

Lines 65–66 
# reset the empty input holder
select_result = uselect.select([stdin], [], [], 0)

After handling one character (or, more precisely, at the end of each outer-loop iteration’s body — see control-flow note below), the code re-polls stdin and stores the fresh result in select_result. This both:

  • feeds the next evaluation of while select_result[0] so multiple buffered bytes can be drained in one outer iteration, and
  • clears the “holder” when the queue is empty so the inner while stops
Indentation detail: in the source file, line 66 sits at the outer while True indent level (same as the first select), not inside the character-handler branches. That means: enter outer loop → poll → while data remains, read & handle one char → after the inner while exits, poll again once → outer loop repeats. The trailing poll on line 66 is somewhat redundant with the poll at the top of the next outer iteration, but keeps select_result updated after draining.
Important MicroPython nuance: the condition while select_result[0]: does not re-call select by itself. After reading one character, select_result still holds the old readable list until line 66 runs — which is only after the inner while body finishes… but the body does not update select_result before looping again. In practice this can mean the inner while keeps iterating with a stale truthy select_result[0] even after the buffer is empty, causing stdin.read(1) to block until another byte arrives (or return empty depending on platform). If you observe hangs between frames, move the re-poll to the end of the inner loop body (or break when read(1) returns empty). As written, the PC’s continuous stream of characters often masks the issue.

9. Serial Protocol Parser (lines 48–64)

Inside the drain loop, each character is dispatched by an if / elif chain. Priority order matters: if hand is already '1' or '2', the current character is treated as a finger count, not as a new hand-select or test key — even if that character happens to be '1', '2', 'L', or 'R'.

Lines 48–52 
# if one hand shows up
if hand == '1':
    # reset the number of hands
    hand = '0'
    turn_on_LEDs(left_LEDs, input_character)

When a previous character set hand to '1', this branch consumes the current character as the left-bank finger count. It immediately clears the pending state (hand = '0') and calls turn_on_LEDs(left_LEDs, input_character). Example PC payload b'13': first byte sets hand='1'; second byte '3' reaches this branch and lights three left LEDs.

Lines 53–56 
# if two hands show up
elif hand == '2':
    hand = '0'
    turn_on_LEDs(right_LEDs, input_character)

Same pattern for hand slot 2 / right LED bank. PC payload b'24' → select right, then light four right LEDs.

Lines 57–59 
# input the number of hands
elif input_character == '1' or input_character == '2':
    hand = input_character

Only reached when hand is still '0' (no pending select). If the character is '1' or '2', store it in hand and wait for the next byte to supply the count. No LEDs change on this character alone.

Lines 60–62 
# turn all lights on for one hand for testing
elif input_character == 'L':
    turn_on_LEDs(left_LEDs, 5)

Test / fill command: light all five left LEDs. The PC companion currently sends 'L' when no hands are detected (see PC docs) — so in the full demo this branch often means “no vision detection,” not merely a manual test, despite the comment.

Lines 63–64 
elif input_character == 'R':
    turn_on_LEDs(right_LEDs, 5)

Same for the right bank. The PC sends 'R' when exactly one hand is visible (after updating the left bank), which fills all right LEDs rather than turning them off.

Characters with no handler

Any other character — including the PC’s per-frame 'V' heartbeat — falls through all branches and is ignored. No error is raised; the loop simply continues.

Protocol summary (PC → STEPico)

BytesFirmware action
'1' then '0'–'5' Select left bank; light that many left LEDs (0 = all left off)
'2' then '0'–'5' Select right bank; light that many right LEDs
'L' All five left LEDs on
'R' All five right LEDs on
'V' or other No-op (ignored)

10. Hand State Machine

The variable hand implements a two-state handshake that turns a stream of single bytes into paired (bank, count) commands.

hand = '0' (idle)
Receive '1' or '2' → hand becomes that digit (armed)
Next byte → apply count to left or right bank; hand = '0'
Or, while idle, 'L' / 'R' bypass the pair and fill a bank
Current handIncoming charNext handSide effect
'0' '1' '1' None (wait for count)
'0' '2' '2' None (wait for count)
'0' 'L' '0' Left bank all on
'0' 'R' '0' Right bank all on
'1' any (e.g. '3') '0' turn_on_LEDs(left_LEDs, char)
'2' any (e.g. '4') '0' turn_on_LEDs(right_LEDs, char)
Because the armed states treat any next character as a count, a desynchronized stream can mis-apply commands. Example: if a count byte is dropped and the next frame’s '1' arrives while hand is still '1', that '1' is interpreted as “light 1 left LED” instead of “select left.” Continuous PC traffic plus the ignored 'V' usually recovers within a frame or two, but there is no explicit resync token.

13. Usage Notes

Requirements

  • STEPico or Raspberry Pi Pico (RP2040) with MicroPython installed
  • Ten LEDs (plus series resistors) wired to the GPIO map above, or a lab board with those pins pre-connected
  • USB cable for power and CDC serial
  • Optional: Thonny IDE to load and run the script
  • Companion PC script ch4-finger-detection-pc.py for the full vision demo

Run — firmware only (manual smoke test)

  1. Open ch4-finger-detection-stepico.py in Thonny.
  2. Select interpreter MicroPython (Raspberry Pi Pico) on the correct COM port.
  3. Click Run. The infinite loop starts.
  4. In the Thonny shell, type characters (they go to stdin):
    • L → all left LEDs on
    • R → all right LEDs on
    • 13 → left bank shows 3 LEDs
    • 20 → right bank all off
    • 25 → right bank all on via count path

Run — full demo with PC vision

  1. Run this firmware on the board (Thonny ▶, or save as main.py for auto-start).
  2. Release the COM port: close Thonny’s serial connection / quit Thonny so the PC script can open the same port.
  3. On the PC, set port in ch4-finger-detection-pc.py to match Device Manager, then run: 
    py ch4-finger-detection-pc.py
  4. Show one or two hands to the webcam; LED banks should track finger counts.
Only one host process can own the USB serial port at a time. Thonny’s REPL and the PC PySerial client will conflict (“Access is denied”) if both try to open the same COM port.

Known quirks in this source

  • time is imported but never used
  • 'V' from the PC is ignored (no branch)
  • PC “no hands” → 'L' lights all left LEDs; it does not call turn_on_LEDs(..., 0)
  • PC “one hand” also sends 'R', filling the right bank
  • No bounds check in turn_on_LEDs for counts > 5
  • Inner while select_result[0] may use a stale poll result until the outer re-poll; consider re-selecting after each read(1) if you see blocking behavior
  • Protocol can desync if a byte is lost while hand is armed
